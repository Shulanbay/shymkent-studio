# Безопасность

## Что реализовано

### Вход и сессии
- Пароли — Argon2id (19 MiB, 2 итерации), минимум 12 символов. Проверка занимает одинаковое время для существующих и несуществующих аккаунтов (защита от перебора email).
- Сессия — случайный 256-битный токен в cookie `HttpOnly`, `SameSite=Lax`, на HTTPS — `Secure` и префикс `__Host-`. В базе хранится только SHA-256 токена.
- Сессия истекает после 24 ч бездействия и в любом случае через 7 дней. Новый токен выдаётся при каждом входе.
- Выход удаляет сессию на сервере (старый cookie больше не работает — проверено E2E). Смена своего пароля завершает остальные сессии. Сброс пароля сотрудника владельцем и `npm run admin:reset-password` завершают все сессии.
- Ограничение попыток входа: 5 на аккаунт и 20 на IP за 15 минут (счётчики в PostgreSQL, IP и email — только в виде хэша).
- Параметр `next` после входа ведёт только внутрь `/admin` (защита от open redirect).
- Вход по ссылке из письма: одноразовый 256-битный токен, в базе только его SHA-256, срок 15 минут, новый запрос отменяет прежние ссылки, повторное использование невозможно (атомарное погашение). Ссылка не срабатывает при открытии (GET), только по кнопке (POST), поэтому почтовые сканеры не могут её «потратить». Ответ одинаков для любых email, лимиты — 3 письма на аккаунт и 10 на IP за 15 минут. Страница ссылки не передаёт Referer.

### Доступ (RBAC)
- Права проверяются на сервере в каждой странице, серверном действии и API (`requirePermission` / `assertPermission`). Middleware — только первая линия: он отсекает запросы без cookie.
- OPERATOR и EDITOR меняют только свои задачи своего этапа. Журнал платежей видят только роли, работающие с деньгами. Возвраты и сторно — только OWNER и ADMIN. Сотрудники и Google-интеграция — только OWNER.

### Формы и API
- Все входные данные проверяются Zod со строгими ограничениями длины. Неизвестные поля (например, цена из браузера) отбрасываются: цену считает только сервер.
- CSRF: публичные POST требуют `Origin` своего сайта. Серверные действия CRM защищены встроенной проверкой Next.js (Origin = Host).
- Публичные формы: лимиты по IP (5 заявок за 10 минут, 60 запросов слотов в минуту), honeypot-поле, ключ идемпотентности, ограничение размера тела (16 КБ).
- IP клиента берётся из `X-Forwarded-For` с учётом `TRUSTED_PROXY_COUNT`: подделанные клиентом записи игнорируются.
- SQL — только через Prisma и параметризованные `$queryRaw` / `$executeRaw`. Сырые строковые запросы есть только в тестах и скриптах обслуживания с жёстко проверенными именами баз.
- Письма: весь пользовательский ввод экранируется; в ссылках допускаются только http(s).
- Ошибки для клиента — безопасные сообщения без stack trace. Детали пишутся в серверный лог.

### Заголовки
- CSP: `default-src 'self'`, скрипты только свои, изображения — свои и превью YouTube, фреймы — только YouTube, `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`, `upgrade-insecure-requests` на HTTPS.
- HSTS (1 год, только на HTTPS), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (камера, микрофон, геолокация, оплата выключены), COOP, CORP.
- CRM, приватные API, health и cron: `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`. `/admin` и `/api` закрыты в `robots.txt` и не попадают в sitemap.
- `'unsafe-inline'` для скриптов остаётся, потому что его требует Next.js. Переход на nonce-CSP отключит статическую генерацию публичных страниц, поэтому не сделан намеренно.

### Данные и секреты
- Токен Google хранится зашифрованным (AES-256-GCM, ключ из `AUTH_SECRET`) и никогда не отдаётся в браузер. OAuth `state` проверяется.
- Логи — JSON без персональных данных: email, телефоны, токены и поля вида name/phone/email заменяются.
- Журнал платежей неизменяем: проведённые записи защищены триггером PostgreSQL; исправление только сторно.
- Двойное бронирование исключено ограничением `EXCLUDE` в базе.
- В production сервер не стартует со слабыми или отсутствующими секретами, localhost-адресами или частично настроенной интеграцией (`lib/env-schema.ts`).
- `.env.local`, `.env`, `.owner-access.local`, резервные копии и артефакты тестов — в `.gitignore`.

### Зависимости
- Next.js обновлён с 14.2 (EOL, критическая уязвимость RCE в оптимизаторе изображений и ряд DoS/SSRF) до 15.5.26. Оптимизатор изображений обслуживает только локальные файлы.
- `npm audit` — 0 уязвимостей. Для вложенных пакетов в `package.json` зафиксированы `overrides`: postcss внутри Next.js и deepmerge-ts внутри Prisma CLI.

## Правила для команды

- Каждому сотруднику — свой аккаунт с минимально нужной ролью. Не передавайте пароли.
- Уволенного сотрудника сразу отключите: «Сотрудники» → снять «Активен» (все его сессии перестают работать).
- Секреты (`AUTH_SECRET`, `CRON_SECRET`, SMTP, Google) храните только в панели хостинга и менеджере паролей.
- Обновляйте зависимости раз в месяц: `npm outdated`, `npm audit`, затем полный прогон тестов.

## Ротация секретов

| Секрет | Как сменить | Последствия |
|---|---|---|
| `AUTH_SECRET` | новое значение в хостинге → перезапуск | сессии остаются; Google Calendar нужно переподключить |
| `CRON_SECRET` | новое значение в хостинге (Vercel передаёт его сам), обновить внешний планировщик | — |
| SMTP / Google client secret | у провайдера → в хостинге | — |
| Пароль сотрудника | «Сотрудники» → «Сменить пароль» | все его сессии завершаются |

## Инцидент (подозрение на утечку доступа)

1. Смените пароль владельца, отключите подозрительные аккаунты.
2. Смените `AUTH_SECRET` и `CRON_SECRET`, пароль SMTP, client secret Google; отзовите доступ приложения в Google Account → Security.
3. Удалите все сессии: `DELETE FROM "Session";` (все выйдут из CRM).
4. Проверьте журнал: «Обзор» → «Последние действия» и таблицу `ActivityLog` (кто и что менял).
5. Если затронуты данные клиентов — действуйте по требованиям закона РК «О персональных данных и их защите» (при необходимости — с юристом).

## Известные ограничения

- Без обратного прокси заголовок `X-Forwarded-For` задаётся самим клиентом, и лимиты по IP становятся приблизительными. Разворачивайте за Vercel, nginx или Caddy.
- Двухфакторная аутентификация для CRM не реализована. Компенсация — длинные пароли, лимиты входа и короткий срок жизни сессий.
- Доставка писем — «хотя бы один раз»: в редком случае сбоя возможен один дубль ([INTEGRATIONS.md](INTEGRATIONS.md)).
