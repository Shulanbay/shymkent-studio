# Резервные копии и восстановление

В базе — заказы, клиенты, платежи и журнал действий. Резервные копии содержат персональные данные: храните их зашифрованными и вне репозитория (`backups/` и `*.dump` в `.gitignore`).

## Два уровня защиты

1. **Провайдер базы (основной):** включите автоматические ежедневные копии и point-in-time recovery (PITR) минимум на 7 дней.
2. **Собственные копии (дополнительно):** `npm run db:backup` по расписанию и хранение в отдельном месте (другой облачный аккаунт или зашифрованный диск).

## Создать копию

```bash
npm run db:backup
# другой каталог или база:
BACKUP_DIR=/secure/backups npm run db:backup
BACKUP_DATABASE_URL="postgresql://…" npm run db:backup
```

- Формат — `pg_dump --format=custom` (сжатый), файл `<база>-<время UTC>.dump` и рядом `.sha256`.
- Существующий файл **никогда не перезаписывается**: скрипт откажется.
- Права на файл — `600`. Пароль передаётся `pg_dump` через переменную окружения, а не в командной строке.
- Нужен `pg_dump` той же или более новой версии, чем сервер (PostgreSQL 16).

Пример ежедневного cron на сервере (03:30 по Шымкенту):

```
30 3 * * * cd /srv/shymkent && BACKUP_DIR=/srv/backups npm run -s db:backup >> /var/log/shymkent-backup.log 2>&1
```

Храните минимум 14 ежедневных и 6 ежемесячных копий. Старые удаляйте вручную или политикой хранилища.

## Проверить, что копия восстанавливается

```bash
npm run db:restore-check                      # самая новая копия из BACKUP_DIR (backups/)
npm run db:restore-check -- backups/x.dump    # конкретный файл
RESTORE_CHECK_DATABASE_URL="postgresql://…тестовый сервер…/postgres" npm run db:restore-check
```

Что делает скрипт:

1. Сверяет контрольную сумму `.sha256`: повреждённый файл не восстанавливается.
2. Создаёт **временную** базу `restore_check_<время>` (по умолчанию на сервере из `DATABASE_URL`; лучше указать отдельный непроизводственный сервер через `RESTORE_CHECK_DATABASE_URL`).
3. Восстанавливает копию, проверяет миграции, количество строк в основных таблицах, защиту от двойного бронирования и триггер журнала платежей.
4. Удаляет временную базу. Исходная база не изменяется, а имена, похожие на рабочие, скрипт использовать откажется.

Запускайте проверку раз в месяц и после каждого изменения процедуры копирования.

## Восстановить после сбоя

1. Остановите запись новых данных: в Docker — `docker stop web worker`; на Vercel — временно удалите `DATABASE_URL` в Production (сайт покажет страницу ошибки, заявки не примутся) или сообщите клиентам в Instagram/WhatsApp.
2. Предпочтительно — PITR провайдера на момент до сбоя (новая база). Иначе — создайте новую пустую базу и восстановите:

```bash
createdb -h HOST -U USER shymkent_restored
PGPASSWORD=… pg_restore --no-owner --no-privileges --exit-on-error -h HOST -U USER -d shymkent_restored backups/<файл>.dump
DATABASE_URL="postgresql://…/shymkent_restored?sslmode=require" npm run db:deploy   # довести миграции, если копия старее кода
```

3. Проверьте данные: последние заказы и платежи в CRM (можно временно запустить локально с этой `DATABASE_URL`).
4. Переключите `DATABASE_URL` в хостинге на восстановленную базу и перезапустите приложение. Проверьте `/api/ready`.
5. Письма из очереди: задачи, созданные после момента восстановления, пропали вместе с данными. Проверьте CRM → «Интеграции» и при необходимости свяжитесь с клиентами вручную.
6. Старую базу не удаляйте, пока не убедитесь, что всё в порядке.

Никогда не восстанавливайте копию поверх рабочей базы: всегда в новую базу, затем переключение.
